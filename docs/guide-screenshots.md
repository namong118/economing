# GUIDE 페이지 스크린샷 캡처 기록

앱 화면이 바뀌면 해당 컷만 다시 캡처. 파일명 동일하게 덮어쓰기.

---

## 캡처 규격

- **뷰포트 430 × 750**, `deviceScaleFactor: 2` → 출력 860 × 1500 (2026-07-28 변경, 이전 430 × 600)
  - 600은 화면 하나가 온전히 안 들어옴(진단 화면 "다음 질문" 버튼, 온보딩 마지막 선택지가
    잘림). 750으로 늘려 여유를 둠. 모바일 모드는 데스크톱의 `zoom:1.10` 배율이 없어 같은
    높이에 더 많은 내용이 들어오므로, 실제로 써보고 너무 많이 남으면 다시 줄인다.
  - 430 × 932라는 최초 숫자는 특별한 근거가 없었음(iPhone 14 Pro Max 기준이었으나
    실기기 검증은 갤럭시 S24로 함). **12장의 크기를 통일하는 것이 목적이지 특정 기기
    재현이 목적이 아님.**
- **12장 모두 동일 치수** — 예전에 384×838과 427×932가 섞여 문제가 된 적 있음
- **뷰포트 자체를 430px로 만들고 그 상태에서 로드해 찍는다.** 데스크톱 화면을 찍은 뒤
  잘라내는 방식이 아님(아래 "캡처 방법" 참고 — 이 부분에서 실제로 한 번 사고가 났음)
- 전체 페이지 캡처(full-page screenshot) 금지
- **로컬 dev 서버**에서 캡처 (`npm run dev`). 배포 사이트는 캐시 때문에 최신 화면이 아닐 수 있어 사용하지 않음
- **실제 사용 계정**으로, 학습 기록이 어느 정도 쌓인 상태에서 캡처
  (진도 0/96이면 빈 화면처럼 보여서 앱의 실제 사용 모습이 안 드러남)
- 저장 위치: `public/guide/`, 파일 형식 PNG

### 캡처 전 필수 검증 (모바일 모드 확인)

이 앱은 `.ds-app`에 데스크톱 전용 스타일이 미디어쿼리로 걸려 있음
(`≥769px`에서 `zoom: 1.10`, `≥1024px`에서 `.ds-brand`가 `display:flex`로 나타나 브랜드
패널이 보임 — 평소엔 `.ds-brand { display: none; }`). 뷰포트가 진짜 430px가 아니면 이
스타일이 걸린 채로 찍히고, 데스크톱 화면을 잘라낸 것과 구분이 안 되는 결과물이 나온다.

**첫 장을 찍기 전에 반드시 확인**:

```js
window.innerWidth                                          // 430이어야 함
document.querySelector('.ds-brand')                        // null 이거나 display:none
getComputedStyle(document.querySelector('.ds-app')).zoom    // 'normal' 또는 1
```

셋 다 통과해야 모바일 모드. 하나라도 안 맞으면 뷰포트가 안 먹은 것이므로 멈추고 확인한다.

### 스크롤바 숨김 — 필수

캡처 직전 CSS 주입. 이걸 안 하면 회색 스크롤바가 찍히고 그만큼 폭이 줄어 치수가 어긋남.

```css
::-webkit-scrollbar { display: none !important; }
* { scrollbar-width: none !important; }
```

## 캡처 방법 (재현용 메모)

브라우저 확장의 `resize_window` 도구는 요청한 폭대로 **탭의 실제 뷰포트**를 바꿔주지
못한다(`window.innerWidth`가 그대로 desktop 폭으로 남음) — 신뢰할 수 없음. `<iframe>`으로
독립된 430px 폭 렌더링 컨텍스트를 만들어 사용한다.

**한 번 실패했던 방식(기록용, 다시 쓰지 말 것)**: iframe을 화면 (0,0)에 430×N 크기로
고정 배치한 뒤, 브라우저 스크린샷 도구의 `zoom(region)` 기능으로 그 영역만 잘라내려 했음.
`zoom`이 요구하는 좌표 단위가 CSS px와 정확히 일치하지 않아(브라우저 자체 배율 등 추정
불가한 배율 차이) 잘라낸 영역이 iframe 경계를 살짝 넘어갔고, 그 결과 iframe 오른쪽에 있는
실제 데스크톱 페이지의 브랜드 패널(PROFILE 메뉴·QR 코드)이 캡처에 섞여 들어갔다. 안전
마진을 조금 줄여도 좌표 단위 자체가 안 맞기 때문에 근본적으로 고쳐지지 않음.

**올바른 방식 — 마젠타 배경 + 자동 트림**:

1. 탭을 로컬 앱의 아무 페이지로 이동(같은 origin이어야 iframe 내부를 스크립트로 조작 가능)
2. `position:fixed; inset:0; background:#ff00ff; z-index:999999` 인 래퍼 div를 `body`에
   주입 (마젠타는 앱 UI에 쓰이지 않는 색이라 배경과 실제 콘텐츠를 명확히 구분하는 용도)
3. 래퍼 안에 `width:430px; height:750px` 인 `<iframe>`을 넣고 `src`를 캡처할 경로로 지정
   — 이 크기가 iframe 내부의 진짜 뷰포트가 되므로, iframe 안에서
   `window.innerWidth === 430` 이 성립함(위 "캡처 전 필수 검증" 참고)
4. 화면 상태(로그인은 공유 세션이라 자동 유지, 스크롤, 클릭 등)를 iframe 안에서 준비
5. 스크롤바 숨김 CSS를 iframe 문서에 주입
6. **`zoom`이 아니라 일반 `screenshot`(전체 화면, region 없음)으로 캡처** — 마젠타 배경이
   iframe 주위를 감싼 채로 찍힘
7. 저장된 이미지를 `sharp(...).trim({ background: {r:255,g:0,b:255} })` 로 마젠타 테두리를
   제거 — 좌표 계산 없이 실제 픽셀 경계를 기준으로 잘라내므로 브라우저 배율 차이와 무관하게
   정확함
8. 그 결과를 860×1500(=430×750의 2배)으로 리사이즈해 치수를 통일, `public/guide/`에 저장

**주의**: 한 번에 몰아서, 창을 리사이즈하지 않고 연속으로 찍을 것 — 화면마다 상태가
달라지면 비교·재현이 어려워짐.

### 2026-07-30 재작업 — 화질 문제 원인과 해결

위 "마젠타 배경 + 트림 + 리사이즈" 방식으로 만든 12장이 확대해보면 글자 가장자리가
심하게 번져 보이는 문제가 있었다(`sharp`로 잘라서 4배 확대해보면 확인 가능). 트림 후
실제 크기가 860×1500과 정확히 안 맞아서 8단계의 리사이즈가 매번 미세하게 보간(resample)
되며 화질이 깎인 것으로 보인다.

**해결**: `chrome-devtools` MCP의 `emulate` 도구가 CDP `Emulation.setDeviceMetricsOverride`를
그대로 노출한다 — `viewport: "430x750x2,mobile,touch"` 하나로 뷰포트·DPR·모바일 모드가
전부 정확히 걸리고, `window.innerWidth === 430`이 실제로 성립한다(브라우저 확장의
`resize_window`와 달리 신뢰 가능). 이러면 iframe도, 마젠타 트림도, 리사이즈도 필요 없이
`take_screenshot`으로 찍은 결과가 처음부터 정확히 860×1500(430×750의 2배, 무손실)으로
나온다. 이후로는 이 방식을 표준으로 쓴다 — 마젠타/트림/리사이즈 방식은 fallback으로만 기록.

## 화면별 주의사항 (실제로 찍으며 알게 된 것)

**04-home** — 홈에는 연속 학습일(스트릭) 표시가 없다. 스트릭은 내 성장 탭에 있음. 원고에 이미 반영됨.

**08-coach** — 질문을 하나 던져 답변을 받은 뒤 캡처해야 한다. 그냥 열면 빈 화면.

**09-roadmap** — "나의 자립 로드맵" 카드가 화면 중심에 오도록 스크롤 조정.

**10-my-growth** — 하단의 "개발자 메뉴"·"로그아웃"이 프레임에 들어가지 않게. 요약 탭 콘텐츠가 짧아 여백이 생기는 지점.

**상단 로고 바 제거 반영** — 로고 바를 없애면 콘텐츠가 60px가량 위로 올라온다. 기존 스크롤 위치 기준은 그만큼 다시 잡아야 함.

## 사용법 페이지 레이아웃 조정

세로가 932 → 750으로 짧아지므로 이미지 배치를 다시 봐야 한다.

- 이미지 표시 폭 320~360px 유지
- 설명 텍스트와 좌우 배치했을 때 높이 균형이 맞는지 확인
- 홀수/짝수 항목마다 좌우를 번갈아 두는 구성 유지
- 이미지 2장(11, 12)이 늘어난 만큼 배치 위치 제안 필요
